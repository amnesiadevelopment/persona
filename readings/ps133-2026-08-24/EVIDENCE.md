# PS-133 — the seed-4242 renderer crash is /dev/shm exhaustion, not the seed

**Ticket:** PS-133 · **Provenance of the report:** PS-128 (`readings/ps128-2026-08-23/EVIDENCE.md` §2, PR #99)
**Measured:** 2026-08-24, in the agent container, against the packaged engine
(`fpchrome.AppImage`) driven through `verify/chromium_tier.ChromiumSession` —
the product's own launch path, not an invented one.

---

## The answer, up front

**The crash does not follow the seed.** It follows `/dev/shm`.

This host's `/dev/shm` is **64 MiB** (Docker's default). Chromium puts its
renderer transport surfaces, its GPU command buffers and the font-data
service's memory there. Below that ceiling chromium does not degrade and does
not refuse to start — it dies **part-way through a page** with

```
TargetClosedError: Target page, context or browser has been closed
```

which names no cause at all. The cause is only in chromium's stderr, which no
record captured:

```
FATAL:components/services/font_data/font_data_service_impl.cc:377]
      Check failed: . : No space left on device (28)
```

preceded by a storm of
`ContextResult::kFatalFailure: CommandBufferHelper::AllocateRingBuffer() failed`.

Seed 4242 was not the cause. It was the configuration that happened to be in
the chair when a constant, invisible, host-level limit ran out.

---

## 1. The death site is `pixelscan.net`, not CreepJS

Before re-measuring anything, the committed PS-128 records answer a question
the ticket's framing gets slightly wrong. Per-checker states, all three runs,
seed 4242 (`readings/ps128-2026-08-23/run*/reading.chromium.windows.seed4242.json`):

| checker | state | reason |
|---|---|---|
| `pixelscan.net` | `read=0`, `unobtainable=12` | `TargetClosedError: Page.inner_text: …` |
| `creepjs` | `read=0`, `unobtainable=9` | **`never_asked: true`** — "the browser session ended mid-run and this checker was NEVER ASKED" |

CreepJS is **downstream collateral**, not the victim: the session was already
dead when its turn came. The renderer dies **during pixelscan.net**.

This matters practically — a repro pointed at CreepJS does not reproduce, which
cost this investigation a full live run before the records were read carefully.
It also has precedent: `checker_cli.py`'s own exit-code docstring records
PS-110 as *"pixelscan crashed the Chromium renderer, every checker sequenced
after it died with the context"*. Same page, same shape, same tier.

The seed-1337 arm reads `pixelscan.net` `read=7` and `creepjs` `read=9` — which
is what made the correlation look clean.

## 2. The seed's entire footprint is four integers

Before measuring, the search space was bounded. `build_chromium_layer` builds
ten extensions; the seed reaches exactly four of them. Building the layer for
both seeds and diffing every generated byte:

```
DIFF .persona-audio-ext/audio.js    (9846 vs 9846 bytes)
DIFF .persona-device-ext/device.js  (26354 vs 26354 bytes)
DIFF .persona-gpu-ext/gpu.js        (42531 vs 42531 bytes)
DIFF .persona-webgl-ext/webgl.js    (12522 vs 12522 bytes)
```

Every one of those diffs is a single line: `var SEED = 1337;` → `var SEED = 4242;`.
Identical byte lengths, one integer each. All ten extensions **build cleanly**
for both seeds — no builder raises, so there is no build-time failure to find.

Three seed-derived candidates were then checked and **falsified by
measurement**, and are recorded here so nobody re-derives them:

* **The WebGL decimation loop** (`webgl.js`, `var takeOdd = (SEED >>> (lvl & 31)) & 1`)
  is the only place the seed changes *control flow* rather than a value — the
  obvious suspect. Extracted and driven in node at 1,000,000 eligible bytes for
  both seeds: **7–8 ms, terminates**, `phase < step` invariant holds. Not it.
* **The GPU pick** (`gpu.js`): both seeds select the **same** GPU
  (`NVIDIA GeForce RTX 3070`). Not it.
* **"A bigger spoofed screen needs more shared memory"** — plausible, and
  **backwards**. The *crashing* seed picks the **smaller** surface:

  | seed | screen | cores | deviceMemory | outcome in PS-128 |
  |---|---|---|---|---|
  | 4242 | 1440×900 (1.30 MP) | 6 | 8 | crashed |
  | 1337 | 2560×1440 (3.69 MP) | 8 | 8 | survived |

  The hypothesis predicts the opposite of the observation, so it is discarded
  rather than kept as a story that happens to fit.

## 3. The discriminating experiment

Live, real engine, through the exit, against `pixelscan.net` — the actual death
site. One seed per process, so a crash cannot contaminate the next.

**Arm A — as-is (64 MiB `/dev/shm`):**

| seed | 4242 | 1337 | 1 | 7 | 99999 | 31337 |
|---|---|---|---|---|---|---|
| outcome | CRASH | CRASH | CRASH | CRASH | CRASH | CRASH |

**Six of six.** Peak `/dev/shm` use pinned to **64.0 MiB** — the ceiling — on
every one. Note the second column: **seed 1337, the control that survived 3/3
in PS-128, dies here too.** A signal that kills the control cannot discriminate,
which is precisely what makes the original seed attribution unsafe.

**Arm B — the same six configurations with `--disable-dev-shm-usage`** (which
moves those surfaces off shm and onto disk):

```
seed=4242 rep=1  41.0s  OK body=5890      seed=1337 rep=1  47.7s  OK body=5535
seed=4242 rep=2  48.2s  OK body=5522      seed=1337 rep=2  28.9s  OK body=4276
seed=4242 rep=3  30.7s  OK body=4276      seed=1337 rep=3  47.6s  OK body=5535
```

**Six of six complete the page**, including three consecutive clean runs on the
seed the ticket was filed against. One variable moved, and it was not the seed.

## 4. How far this generalises

The ticket asks explicitly whether other seeds can reach the same state and
roughly how many, because a fix that rescues one integer leaves the defect in
the field.

**Every seed can reach it.** This is not an estimate from a sample: the failure
is a host resource ceiling that the seed does not influence, and the six seeds
tried spanned small, large and adjacent values with a 6/6 failure rate. There
is no "neighbouring bad value" to avoid and no safe range to steer toward —
which is also why seeding around it was never an option.

## 5. What was changed, and what deliberately was not

The defect being fixed is **not** "chromium crashes" — that is the host's
`/dev/shm`, which persona does not own and cannot resize from inside the
container. The defect is that **the tier turned a host limit into a false
statement about the product**, and did so convincingly enough to survive three
runs and produce a ticket.

So the fix makes the misattribution impossible rather than making the crash
invisible:

* `dev_shm_bytes()` probes the host's `/dev/shm` **capacity** (not free space —
  otherwise the answer depends on who else is on the box).
* A launch below `MIN_DEV_SHM_BYTES` raises **`DevShmTooSmall`** *before*
  anything starts, naming the actual number (`"this host's /dev/shm is 64 MiB"`)
  and the waiver that recovers it.
* `--allow-small-dev-shm` runs anyway with `--disable-dev-shm-usage`, is
  **never inferred**, and is **disclosed on the record** — because that flag is
  not on persona's own launch path, so a reading taken under it is not the
  product's surface.

This mirrors, deliberately and line for line, the existing
`sandbox_available()` / `SandboxUnavailable` / `--allow-unsandboxed-chromium`
idiom in the same module. It is the same class of problem — a host condition
that makes chromium fail in a way that reads as a product fault — and it gets
the same shape of answer rather than a second, differently-spelled one.

**Explicitly not done**, per the ticket's boundaries: no retry, no catch, no
seed avoidance. A retry loop would convert a 6-of-6 reproducible failure into
an intermittent one — strictly worse, because the next person to see it could
not reproduce it the way this ticket could.

## 6. Limits of this reading — stated, not buried

* **The sandboxed reproduction the ticket asks for first could not be done
  here.** This host returns `EPERM` from `unshare(CLONE_NEWUSER)` (confirmed
  directly; `max_user_namespaces` is 63458 and
  `unprivileged_userns_clone` is 1, so it is a restriction, not exhaustion), so
  every run above required `--allow-unsandboxed-chromium` — the same caveat
  PS-128 carried. A renderer crash is genuinely a class of failure an
  unsandboxed process can produce differently. What makes the conclusion hold
  anyway is that the mechanism is **named in chromium's own stderr** and is
  removed by a flag that targets exactly that mechanism — not inferred from the
  crash's timing.
* **PS-128's seed *selectivity* was not reproduced.** Their seed 1337 passed
  3/3; here it fails like every other seed. This is expected of a threshold
  resource: which configuration tips over depends on how much shm is left at
  that moment — page weight, checker order, what else is resident — not on any
  derived value. It is **not** a claim that their records are wrong. They
  recorded what they saw; the axis they varied simply was not the one that
  mattered, and nothing in the record could have told them so.
* **`MIN_DEV_SHM_BYTES = 256 MiB` is a margin, not a measured knee.** What was
  measured is the endpoint pair only: 64 MiB fails 6/6, and the workaround
  succeeds 6/6. Raising the ceiling to find the true knee needs `CAP_SYS_ADMIN`
  this container does not have (`mount -o remount,size=1g /dev/shm` is denied).
  The constant sits deliberately clear of the one value known to fail.
* The exit went down mid-session (`ERR_SOCKS_CONNECTION_FAILED`, confirmed
  independently of persona with three direct `curl` attempts through the same
  credential). Per the project's proxy rule that is reported, not worked
  around; all evidence above was captured before it dropped.

## 7. What this unblocks

PS-128 could not take the two-seed Chromium WebGL reading PS-97 requires
because one arm never rendered. On this host that arm now renders — seed 4242
completed `pixelscan.net` three times consecutively. Taking that reading
remains **out of scope here** and belongs to whoever picks it up, exactly as
the ticket directs.

Anyone taking it should note that it must be taken either on a host with
adequate `/dev/shm`, or with `--allow-small-dev-shm` — in which case the record
will say so, and the comparison should be read with that disclosure in view.
