NOTE FOR HONEST BOUND 2 (raised WITH the reading, as the ticket requires).
The pair does not merely look impossible — the window's TRUE extent is
readable from it. A page that sees outerWidth 1919 while screen.width claims
1280 learns the real window is 1919 CSS px, i.e. the host window size the
FORCED branch was meant to conceal. That is a stronger statement than
"incoherent", and it is why capping/pinning is worth doing rather than
tolerating. It is still MASKING INVISIBILITY, not an Invariant #0 host-fact
leak: no GPU, OS, locale or IP escapes, and outerWidth is the host WINDOW,
which the operator controls. Recorded here rather than silently upgraded.

1919 not 1920: chromium's own window chrome under this WM. Immaterial —
the comparison under test is outer vs screen, and 1919 > 1280 either way.

=====================================================================
Reviewer (persona-reviewer, audit FAIL on PR #266 @ 392ce47) found that the
round-1 fix — clamping the REPORTED outer down to the spoofed screen — bought
R3 by breaking R1. Reproduced independently here with the same builder:

   pick          inner        outer       screen    oW-iW  oH-iH  R1
   win 1280x720  [1919,936]  [1280,680]  [1280,720]  -639   -256  VIOLATED
   win 1366x768  [1919,936]  [1366,728]  [1366,768]  -553   -208  VIOLATED
   win 1600x900  [1919,936]  [1600,860]  [1600,900]  -319    -76  VIOLATED
   mac 1440x900  [1919,936]  [1440,875]  [1440,900]  -479    -61  VIOLATED

ATTRIBUTION, checked at the merge-base d658c81 (the "broke it vs exposed it"
rule): R1 HELD at base (oW-iW = 0) while R3 was the violation. So round 1's
breakage was mine and in scope, not debt it exposed.

WHY IT WAS NOT A SLIP IN THE CLAMP — IT IS ARITHMETIC:
   live inner 1919, picked screen 1280
   R1 needs outer >= 1919
   R3 needs outer <= 1280
   => 1919 <= outer <= 1280 is EMPTY.
No value the content script reports satisfies both. Bounding the clamp below
by inner (the obvious repair) only chooses R3's violation instead of R1's.

THE ROOT IS R2 (inner <= screen), and `inner` is the real window's content
box — not spoofable at the reporting layer without breaking layout on real
pages. So the reporting layer is the WRONG LAYER for this vector.

MEASURED FIX — CAP THE WINDOW. Live under Xvfb, window sized to the pick:
   CAP to 1280x720:  inner [1280,577]  outer [1280,680]  screen [1280,720]
      R1  1280 >= 1280  OK
      R2  1280 <= 1280  OK   <-- even the PRE-EXISTING violation clears
      R3  1280 <= 1280  OK
All three hold simultaneously, which the reporting layer provably cannot do.

A FACT I GOT WRONG IN ROUND 1, corrected: I rejected the cap partly because I
believed the desktop branch could not know the resolution at launch. It CAN —
process.py's desktop `else` arm already computes
parse_resolution(profile.resolution) to build the extension, so the value is
in hand exactly where launch args are assembled.

RESULT: device_ext.py is now BYTE-IDENTICAL to base. The whole fix is one
launch arg in process.py, fired only when a desktop profile carries a FORCED
resolution (parse_resolution("auto") is None, so AUTO cannot reach it).
