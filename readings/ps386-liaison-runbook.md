# PS-386 — liaison runbook: macOS hardened runtime + `get-task-allow`

**For the host-liaison, to run on the owner's Mac (macOS 26.6.2, arm64).**
The agent did the code seam and wired it into the release job; this file is the
handover for the half that needs a real machine. Nothing below needs a
credential, and nothing below produces a signed or notarized artifact.

⛔ **Read the two outcome rules before you start, because they decide how to
report — and one of them is counter-intuitive:**

1. **A build that succeeds while the app cannot launch is a FAILURE, not a pass.**
2. ⭐ **A run where it does NOT work is an equally genuine delivered outcome.**
   Record what failed and which entitlement or exception it would need. **Do not
   weaken the posture until the checker goes green** — a real incompatibility
   converted into a green build is the one result this slice must not produce.

## What changed in the tree

| file | what it does |
|---|---|
| `pyproject.toml` → `[tool.flet.macos.entitlement]` | declares the six-key entitlement set explicitly (was: no `[tool.flet.macos]` at all, so persona contributed nothing) |
| `scripts/ps386_macos_harden.py` | **new.** Re-signs *our* slices with `--options runtime` and the entitlements above |
| `scripts/ps386_verify_posture.py` | **new.** Reads the produced bytes with PS-346's own readers and gates on them |
| `.github/workflows/release.yml` → `build-macos` | **four new steps.** The scripts are actually invoked, and the frozen-bundle smoke test now runs a second time *after* hardening |
| `tests/test_ps386_macos_harden.py` | **new.** 56 tests; every load-bearing one proven to fail against a deliberate mutant |

⛔ `scripts/ps346_signing_state.py` is **untouched** — it is the control for the
before/after reading. Verify with `git diff --name-only` if you want to be sure.

### Why two mechanisms and not one

`pyproject.toml` alone **cannot** turn on the hardened runtime.
`ENABLE_HARDENED_RUNTIME` and `OTHER_CODE_SIGN_FLAGS` occur **nowhere** in
flet-cli 0.85.3 **nor** in its build template v0.85.3 (re-measured this session
against the downloaded sdist: zero hits in both), and flet exposes no
xcode-build-setting passthrough of any kind. The generated Xcode project lives
under `build/`, which is gitignored and regenerated by every `flet build` — so
editing it "works" exactly once and is silently reverted. **Re-signing the
produced `.app` is the only seam that survives regeneration.** That is why there
is a script.

### ⭐ Why there are now TWO scripts, not one

The hardener **asserts** a posture; it cannot **measure** one. `codesign`
exiting 0 says the tool accepted its arguments — it does not say the produced
CodeDirectory carries `CS_RUNTIME`, and it certainly does not say the
entitlements blob lost `get-task-allow`. That matters specifically because
**ad-hoc `codesign` is what injects `get-task-allow` in the first place**, so a
build can carry the hardened runtime and *still* be rejected by the notary.

So `ps386_verify_posture.py` reads the produced bytes, using PS-346's audited
readers imported **unmodified**. It is a *caller* of the control (explicitly
allowed), never an edit to it and never a second hand-rolled reader.

### ⭐ Why the smoke test now runs twice

Hardening re-signs the compiled extensions inside the bundle's own
site-packages — the very `.so` files `smoke_frozen_bundle.py` imports. The
pre-hardening run therefore validated bytes that are **not** the ones shipping.
The second run is the falsification step: if re-signing broke an import, or the
hardened runtime's library validation refuses one, it surfaces before `hdiutil`,
before checksums and before publish.

⚠️ **Its documented bound is unchanged and still applies:** it exercises the
frozen *Python* payload under an ABI-matched interpreter, **not** the Flutter
host layer. It is **necessary and not sufficient** for outcome 4 below. A green
CI run must never be reported as "the app launches".

## Step 0 — confirm the origin on the build host (PS-386 outcome 1)

This is the one step whose answer the agent could only infer. Everything else
was settled from Linux by set-difference; **this observes it.**

### ⛔ IT MUST BE RUN AT THE MERGE-BASE, NOT ON THIS BRANCH

This branch's `pyproject.toml` now carries `[tool.flet.macos.entitlement]` with
`get-task-allow = false`, and that block is a **live merge seam** — flet merges
it over its own five defaults, so a `flet build macos` **on this branch** writes
a generated `Release.entitlements` that already mentions the key. That is not a
baseline: it is our own commit showing up in the reading.

The question Step 0 exists to answer is *"does ad-hoc `codesign` inject
`get-task-allow` when **nothing** declares it?"* — and that reading is only
obtainable on a tree where nothing declares it.

```bash
cd <persona repo>
# A separate checkout at the merge-base, so the branch stays intact.
git worktree add /tmp/ps386-base d300635
cd /tmp/ps386-base
git rev-parse --short HEAD        # expect d300635
grep -n "flet.macos" pyproject.toml || echo "no [tool.flet.macos] — correct baseline"

ver="$(python3 -c "import re,pathlib; print(re.search(r'APP_VERSION\s*=\s*\"([^\"]+)\"', pathlib.Path('src/services/app_update/updater.py').read_text()).group(1))")"
flet build macos -v --no-rich-output --build-version "$ver"

APP="$(find build/macos -maxdepth 3 -name '*.app' | head -1)"; echo "$APP"

# ⭐ THE ORIGIN QUESTION, asked where it can be answered:
#    does the GENERATED plist carry get-task-allow when nothing declared it?
find build -name "Release.entitlements" -exec sh -c 'echo "--- {}"; cat {}' \;

# ...and does the SIGNED binary carry it?
codesign -d --entitlements :- "$APP" 2>/dev/null
codesign -dvvv "$APP" 2>&1 | grep -i "flags\|Authority"
```

**The discriminator, stated for what will actually be on screen at `d300635`:**

- **ABSENT from the generated plist, PRESENT AND TRUE in the signed binary** →
  origin confirmed as **signing-time injection** by ad-hoc `codesign`. The
  re-sign is the correct seam. **This is the expected result**, and it is what
  the set-difference predicts.
- **PRESENT in the generated plist** → the set-difference is wrong somewhere: a
  source contributes the key after all. **Stop and report that** — the seam
  choice needs revisiting.

Expect `flags=0x2(adhoc)` and no `runtime` in this baseline. Keep this `$APP`
around: it is the "before" side of Step 3.

Then return to the branch for Steps 1–4:

```bash
cd <persona repo>          # the PS-386 branch checkout
git worktree remove /tmp/ps386-base --force   # when you are done with it
```

## Step 1 — baseline reading, on the branch

```bash
cd <persona repo>            # the PS-386 branch
ver="$(python3 -c "import re,pathlib; print(re.search(r'APP_VERSION\s*=\s*\"([^\"]+)\"', pathlib.Path('src/services/app_update/updater.py').read_text()).group(1))")"
flet build macos -v --no-rich-output --build-version "$ver"
APP="$(find build/macos -maxdepth 3 -name '*.app' | head -1)"

python3 scripts/ps386_macos_harden.py --check-pyproject   # sanity, runs anywhere
python3 scripts/ps386_macos_harden.py --app "$APP" --dry-run
python3 scripts/ps386_verify_posture.py --app "$APP"      # expect FAIL — the baseline
```

`--dry-run` reports **four** counts — two of them ours, two of them skips — and
the last is the one to read carefully:

| bucket | ours? | meaning |
|---|---|---|
| `ADHOC` | ✅ | signed by `-`, no identity — will be re-signed |
| `UNSIGNED` | ✅ | **no signature at all** — will be re-signed; this is the compiled Python extensions |
| `THIRD_PARTY` | ❌ | a real certificate signed it; **named**, so you can see whose |
| `UNREADABLE` | ❌ | `codesign` could not tell us — **left alone, but this is not a third-party skip** |

⛔ **THE TWO TOOLS COUNT DIFFERENT THINGS, AND THE TABLE ABOVE IS IN THE
DRY-RUN'S UNIT.** Read this before you compare any number to PS-346:

| counter | unit | why |
|---|---|---|
| `--dry-run`'s `ADHOC` / `UNSIGNED` / `THIRD_PARTY` / `UNREADABLE` | **ITEMS** — one per file or nested bundle directory | `classify()` is called once per *path* |
| PS-346's `ADHOC=196, UNSIGNED=28, SIGNED_CMS=1` | **ARCH SLICES** — one per architecture inside a file | `macho_slices()` returns one entry per fat-binary arch |

**A universal binary is one item and two slices.** The vocabulary is shared on
purpose — the two tools name the same four states — but **the counts are not
interchangeable and must be translated.**

⭐ **`UNSIGNED` must not be zero, and a zero there is a defect rather than good
news.** PS-346 measured this bundle as `ADHOC=196, UNSIGNED=28, SIGNED_CMS=1`
**slices**, and the 28 are the compiled Python extensions
(`aiohttp/_http_parser.cpython-312-darwin.so` and siblings) — ours, shipped with
no signature, and the slices most in need of the hardened runtime. They reach
the classifier through a **non-zero `codesign` exit** (`code object is not
signed at all`), which is an answer rather than an error; a version of this
script that read it as an error skipped all 28 and then failed Step 3 on them.
**If `UNSIGNED` reads 0, stop and report it** — do not proceed to Step 2.

**Translating those slices into the items you will actually see** — stated as
arithmetic, so that a *correct* reading is never mistaken for a broken
classifier:

```
PS-346's committed artifact:  113 Mach-O files  ->  225 arch slices
  113 x 2 = 226 vs 225 measured  =>  exactly ONE thin file
  and it is `node`, the lone SIGNED_CMS.
  So:  196/2 = 98 ADHOC  +  28/2 = 14 UNSIGNED  +  1 THIRD_PARTY  =  113  ✓ exact
```

⭐ **So expect `UNSIGNED` ≈ 14 items and `ADHOC` ≈ 98 items** — roughly half of
PS-346's slice figures, because these binaries are universal (`arm64` +
`x86_64`, ~2 slices per file).

⚠️ **If you see `UNSIGNED` ≈ 28 and `ADHOC` ≈ 196 instead, that is ALSO correct**
— it means this build is **thin-arch**, the ratio is 1:1, and item counts equal
slice counts. Nothing is broken; report which one you saw.

⛔ **The defect is a ZERO, and only a zero.** Neither ~14 nor ~28 is the stop
condition. ⭐ **And one command settles the unit outright, in either direction:**

```bash
find "$APP" -type f -exec sh -c 'file "$1" | grep -q Mach-O && lipo -archs "$1" 2>/dev/null' _ {} \; | sort | uniq -c
```

Two archs per line → universal, expect the ~14 reading. One arch per line →
thin, expect the ~28 reading. **Nobody has read this bundle's `lipo -archs`
yet**, which is why both readings are written down rather than one.

⚠️ **`UNREADABLE` is not a synonym for `THIRD_PARTY`.** Both are skipped, so the
signing decision is the same, but an unreadable slice is one we might have been
able to harden and did not. **Report the count.** A non-zero one means the final
"re-signed N" line is complete over what the run could classify, not over the
bundle — and the verifier in Step 3 will fail on any such slice that ships
without the runtime flag, which is the intended way for the shortfall to
surface.

Expect exactly **one** `THIRD_PARTY`: Node.js Foundation's `node`, vendored under
playwright's driver. (Microsoft's signed DLLs are real but live in the *Windows*
engine zip — they are not in this bundle, and seeing them here would itself be a
finding.)

The verifier is **expected to exit 1 here.** That is the baseline, not an error.

## Step 2 — apply the hardening

```bash
python3 scripts/ps386_macos_harden.py --app "$APP"
echo "exit=$?"
```

Exit codes: `0` all targeted items re-signed and the bundle verifies · `1` an
item failed · `2` **the environment could not run it — this is NOT a pass.**

⭐ **What to watch for:** the script signs nested bundles **at their root** and
**deepest-first**. PS-346 measured **20 `_CodeSignature/CodeResources` seals**
inside this one `.app` — it is a tree of bundles, not one bundle. If you see
`codesign --verify --deep --strict` fail with a *stale seal* or *code object is
not signed at all* complaint, that ordering is the first thing to report.

## Step 3 — the before/after reading (non-waivable)

```bash
python3 scripts/ps386_verify_posture.py --app "$APP"; echo "verify=$?"

# and the raw codesign view, for the record
codesign -dvvv "$APP" 2>&1 | grep -i "flags\|Authority"
codesign -d --entitlements :- "$APP" 2>/dev/null
codesign --verify --deep --strict --verbose=2 "$APP"; echo "deep=$?"
```

**The two figures to move:**

| | before | after |
|---|---|---|
| `runtime (0x10000)` | `False` | expect `True` |
| `get-task-allow` | `true` on our slices | expect absent/false |

`flags` should read `0x10002` (`0x2` adhoc + `0x10000` runtime), and the
signature is still **ad-hoc with no Authority** — that is correct and expected.

⚠️ `scripts/ps346_signing_state.py` in its committed form downloads the
**published v3.1.1 assets** (`APP_TAG`/`APP_ASSETS`) — it does not take a local
`.app`. Running it unchanged re-measures the *old published* bundle, which is
the correct "before" side but is **not** a reading of what you just built. ⛔
**Do not edit its readers to point it at a local path** — that invalidates the
control. `ps386_verify_posture.py` is the permitted *caller* that reads a local
build with those same readers; use it, and report both if you want the published
baseline too.

## Step 4 — ⭐ THE ACTUAL POINT: does it still run?

Steps 2–3 are worthless without this. The hardened runtime restricts JIT,
unsigned executable memory and `DYLD_*` injection; persona ships a **bundled
CPython** and **spawns a browser engine as a subprocess** — precisely the shapes
that break.

```bash
open "$APP"                       # must actually paint a window
# then, in the UI: create/open a profile and LAUNCH it.
```

**Observe and report, in order:**

1. Does the app **launch and paint a window**? (A zombie process with no window
   is a failure — there is prior art for exactly that shape on this app.)
2. Does launching a profile **spawn a Personium engine**? Confirm the child
   process exists:
   ```bash
   pgrep -fl -i "personium|chrom|firefox" | head
   ```
3. If either fails, capture the reason — this is a **genuine delivered outcome**:
   ```bash
   log show --predicate 'eventMessage CONTAINS "persona" OR eventMessage CONTAINS "taskgated" OR eventMessage CONTAINS "AMFI"' --last 10m --style compact | tail -60
   ```
   `AMFI`/`taskgated`/`Library Validation`/`codesign` denials name which
   entitlement or exception would be needed (likely candidates:
   `cs.allow-unsigned-executable-memory`, `cs.disable-library-validation`,
   `cs.allow-dyld-environment-variables`).

⛔ **If it breaks, report which entitlement it would need — do not add
entitlements until it passes.** That decision comes back to the ticket.

### ⚠️ One more thing worth checking, and it is not in the ticket

persona **self-updates by rewriting its own bundle** (`_apply_macos` swaps the
installed `.app` for the one inside a verified dmg). A hardened, sealed bundle
is stricter about being modified in place than an unsealed one. The swap
replaces the whole `.app` rather than editing files inside it, which *should* be
fine — but it has never been observed under a sealed bundle. **If you have the
time, exercise one update cycle** and report what happens. If you do not, say so
rather than assuming; an unobserved path is unobserved.

## Standing constraints (unchanged)

- ⛔ **No credential** acquired, held, placed or echoed. The scripts can only
  sign ad-hoc (`--sign -`) and have no path to a real identity — asserted by a
  test, including one that scans the workflow itself.
- ⛔ **This produces no signed or notarized artifact** and must not be reported
  as one. Notarization still needs the Apple Developer Program membership, which
  is the owner's decision and out of scope. What this removes is the two
  blockers that would make such a submission fail *even with* the identity.
- ⛔ **Do not blanket-remove entitlements** to make a checker green.
  `cs.allow-jit` is very probably required by the bundled interpreter.
- ⚠️ **Invariant #0 stays open and unclaimed.** If you observe that
  `get-task-allow` let a local process read profile state or the operator's
  identity, raise it **with the reading attached** — never in anticipation.
