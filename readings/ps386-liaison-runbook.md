# PS-386 — liaison runbook: macOS hardened runtime + `get-task-allow`

**For the host-liaison, to run on the owner's Mac (macOS 26.6.2, arm64).**
The agent did the code seam; this file is the handover for the half that needs a
real machine. Nothing below needs a credential, and nothing below produces a
signed or notarized artifact.

⛔ **Read the two outcome rules before you start, because they decide how to
report — and one of them is counter-intuitive:**

1. **A build that succeeds while the app cannot launch is a FAILURE, not a pass.**
2. ⭐ **A run where it does NOT work is an equally genuine delivered outcome.**
   Record what failed and which entitlement or exception it would need. **Do not
   weaken the posture until the checker goes green** — a real incompatibility
   converted into a green build is the one result this slice must not produce.

### Why two mechanisms and not one

`pyproject.toml` alone **cannot** turn on the hardened runtime.
`ENABLE_HARDENED_RUNTIME` and `OTHER_CODE_SIGN_FLAGS` occur **nowhere** in
flet-cli 0.85.3 **nor** in its build template v0.85.3 (measured: zero hits in
both), and flet exposes no xcode-build-setting passthrough of any kind. The
generated Xcode project lives under `build/`, which is gitignored and
regenerated by every `flet build` — so editing it "works" exactly once and is
silently reverted. **Re-signing the produced `.app` is the only seam that
survives regeneration.** That is why there is a script.

## Step 0 — confirm the origin on the build host (PS-386 outcome 1)

This is the one step whose answer the agent could only infer. Everything else
was settled from Linux by set-difference; **this observes it.**

```bash
cd <persona repo>
git rev-parse --short HEAD        # expect the PS-386 branch tip

# Build ONCE without the hardening, to capture the baseline the ticket cites.
ver="$(python3 -c "import re,pathlib; print(re.search(r'APP_VERSION\s*=\s*\"([^\"]+)\"', pathlib.Path('src/services/app_update/updater.py').read_text()).group(1))")"
flet build macos -v --no-rich-output --build-version "$ver"

APP="$(find build/macos -maxdepth 3 -name '*.app' | head -1)"; echo "$APP"

# ⭐ THE ORIGIN QUESTION: does the GENERATED plist carry get-task-allow?
cat build/flutter/macos/Runner/Release.entitlements 2>/dev/null \
  || find build -name "Release.entitlements" -exec cat {} \;

# ...and does the SIGNED binary carry it?
codesign -d --entitlements :- "$APP" 2>/dev/null
codesign -dvvv "$APP" 2>&1 | grep -i "flags\|Authority"
```

**What to report:** whether `get-task-allow` appears in the *generated file* or
only in the *signed binary*.

- **Only in the binary** → confirms the agent's set-difference: it is injected by
  ad-hoc `codesign`, and the re-sign step is the correct seam. **This is the
  expected result.**
- **In the generated file too** → the set-difference is wrong somewhere. **Stop
  and report that** — it would mean a source contributes the key and the seam
  choice needs revisiting.

Expect `flags=0x2(adhoc)` and no `runtime` in the baseline.

## Step 1 — baseline reading with PS-346's instrument

```bash
python3 scripts/ps386_macos_harden.py --check-pyproject   # sanity, runs anywhere
python3 scripts/ps386_macos_harden.py --app "$APP" --dry-run
```

`--dry-run` lists which slices would be re-signed and which are **left alone**
because they carry a real third-party identity (Node.js Foundation's `node` is
the known one). **Report those two counts** — the "ours vs theirs" split is the
figure that keeps the target honest at *every slice we build* rather than a
misleading bundle-wide `225/225`.

## Step 2 — apply the hardening

```bash
python3 scripts/ps386_macos_harden.py --app "$APP"
echo "exit=$?"
```

Exit codes: `0` all targeted slices re-signed and the bundle verifies · `1` a
slice failed · `2` **the environment could not run it — this is NOT a pass.**

## Step 3 — the before/after reading (non-waivable)

```bash
codesign -dvvv "$APP" 2>&1 | grep -i "flags\|Authority"
codesign -d --entitlements :- "$APP" 2>/dev/null
codesign --verify --deep --strict --verbose=2 "$APP"; echo "verify=$?"
```

**The two figures to move:**

| | before | after |
|---|---|---|
| `runtime (0x10000)` | `False` | expect `True` |
| `get-task-allow` | `true` on our slices | expect absent/false |

`flags` should read `0x10002` (`0x2` adhoc + `0x10000` runtime), and the
signature is still **ad-hoc with no Authority** — that is correct and expected.

⚠️ `scripts/ps346_signing_state.py` in its committed form downloads the
**published v3.1.1 assets** (`APP_TAG`/`APP_ASSETS`) — it does not take a local
`.app`. Running it unchanged re-measures the *old published* bundle, which is
useful as the "before" side but is **not** a reading of what you just built. ⛔
**Do not edit its readers to point it at a local path** — that invalidates the
control. Use the `codesign` commands above for the local artifact, and report
both. (If a local-path caller turns out to be wanted, that is an added *caller*,
which is allowed, and belongs in its own change.)

## Step 4 — ⭐ THE ACTUAL POINT: does it still run?

Steps 2–3 are worthless without this. The hardened runtime restricts JIT,
unsigned executable memory and `DYLD_*` injection; persona ships a **bundled
CPython** and **spawns a browser engine as a subprocess** — precisely the shapes
that break.

```bash
open "$APP"                       # must actually paint a window
# then, in the UI: create/open a profile and LAUNCH it.
```

**Observe and report, in order:**

1. Does the app **launch and paint a window**? (A zombie process with no window
   is a failure — there is prior art for exactly that shape on this app.)
2. Does launching a profile **spawn a Personium engine**? Confirm the child
   process exists:
   ```bash
   pgrep -fl -i "personium|chrom" | head
   ```
3. If either fails, capture the reason — this is a **genuine delivered outcome**:
   ```bash
   log show --predicate 'eventMessage CONTAINS "persona" OR eventMessage CONTAINS "taskgated" OR eventMessage CONTAINS "AMFI"' --last 10m --style compact | tail -60
   ```
   `AMFI`/`taskgated`/`Library Validation`/`codesign` denials name which
   entitlement or exception would be needed (likely candidates:
   `cs.allow-unsigned-executable-memory`, `cs.disable-library-validation`,
   `cs.allow-dyld-environment-variables`).

⛔ **If it breaks, report which entitlement it would need — do not add
entitlements until it passes.** That decision comes back to the ticket.

## Standing constraints (unchanged)

- ⛔ **No credential** acquired, held, placed or echoed. The script can only sign
  ad-hoc (`--sign -`) and has no path to a real identity — this is asserted by a
  test.
- ⛔ **This produces no signed or notarized artifact** and must not be reported as
  one. Notarization still needs the Apple Developer Program membership, which is
  the owner's decision and out of scope. What this removes is the two blockers
  that would make such a submission fail *even with* the identity.
- ⛔ **Do not blanket-remove entitlements** to make a checker green.
  `cs.allow-jit` is very probably required by the bundled interpreter.
- ⚠️ **Invariant #0 stays open and unclaimed.** If you observe that
  `get-task-allow` let a local process read profile state or the operator's
  identity, raise it **with the reading attached** — never in anticipation.
